-# ticket
-
-## Purpose
-
-Ticket Statuses provides the administrator-only list, create form, and edit form at
-`/setup/ticket-statuses`. The web feature uses the existing `tbltickets_status` records through
-`erp-api/src/v1/ticket-statuses`; it does not add pagination or a separate export API.
-
-## Legacy screen
-
-None: Ticket Statuses is served by the migration API and the existing Node-owned status table.
-
-## Legacy parity
-
-The list shows status ID and name, supports search and sorting, and offers create, edit, and delete
-actions. Built-in statuses remain visible and editable but do not offer Delete. Create and edit
-submissions are confirmed before the API request; a successful save returns to the originating list.
-Search and sorting are local because the backend list contract is an unpaginated `{ data }` response.
-
-## Dropped on purpose
-
-- Pagination query parameters and cursor handling: the API strictly accepts an empty list query.
-- Export: the API has no Ticket Statuses export endpoint.
-- Delete for built-in statuses: the backend also refuses that operation.
-
-## Routes
-
-- `GET /api/v1/ticket-statuses`
-- `GET /api/v1/ticket-statuses/:id`
-- `POST /api/v1/ticket-statuses`
-- `PATCH /api/v1/ticket-statuses/:id`
-- `DELETE /api/v1/ticket-statuses/:id`
-
-The three `/setup/ticket-statuses` pages are gated by `ADMIN_GATE`; the API independently requires
-an administrator for every actor-facing operation.
-
-## Data
-
-The list returns `{ data: TicketStatus[] }`, with no `meta`, `limit`, or `cursor`. The UI validates
-the backend wire fields and maps `ticketstatusid` to its existing row `id`; nullable color and order
-values are adapted to the form's empty color and zero order defaults. Names are limited to 50
-characters. Backend deletion checks protect built-in, ticket-referenced, and configured default
-reply statuses.
-
-## Messages
-
-English and Arabic strings are in `messages/en.json` and `messages/ar.json`. Backend refusal codes
-`ERP-TICKETSTATUSES-0001` and `ERP-TICKETSTATUSES-0002` have feature-specific messages in both
-locales.
-
-## How to run its tests
-
-From `erp-web`, run `corepack yarn vitest run src/features/ticket`.

# ticket

## Purpose

Ticket Statuses provides the administrator-only list, create form, and edit form at
`/setup/ticket-statuses`. The web feature uses the existing `tbltickets_status` records through
`erp-api/src/v1/ticket-statuses`; it does not add pagination or a separate export API.

## Legacy screen

None: Ticket Statuses is served by the migration API and the existing Node-owned status table.

## Legacy parity

The list shows status ID and name, supports search and sorting, and offers create, edit, and delete
actions. Built-in statuses remain visible and editable but do not offer Delete. Create and edit
submissions are confirmed before the API request; a successful save returns to the originating list.
Search and sorting are local because the backend list contract is an unpaginated `{ data }` response.

## Dropped on purpose

- Pagination query parameters and cursor handling: the API strictly accepts an empty list query.
- Export: the API has no Ticket Statuses export endpoint.
- Delete for built-in statuses: the backend also refuses that operation.

## Routes

- `GET /api/v1/ticket-statuses`
- `GET /api/v1/ticket-statuses/:id`
- `POST /api/v1/ticket-statuses`
- `PATCH /api/v1/ticket-statuses/:id`
- `DELETE /api/v1/ticket-statuses/:id`

The three `/setup/ticket-statuses` pages are gated by `ADMIN_GATE`; the API independently requires
an administrator for every actor-facing operation.

## Data

The list returns `{ data: TicketStatus[] }`, with no `meta`, `limit`, or `cursor`. The UI validates
the backend wire fields and maps `ticketstatusid` to its existing row `id`; nullable color and order
values are adapted to the form's empty color and zero order defaults. Names are limited to 50
characters. Backend deletion checks protect built-in, ticket-referenced, and configured default
reply statuses.

## Messages

English and Arabic strings are in `messages/en.json` and `messages/ar.json`. Backend refusal codes
`ERP-TICKETSTATUSES-0001` and `ERP-TICKETSTATUSES-0002` have feature-specific messages in both
locales.

## How to run its tests

From `erp-web`, run `corepack yarn vitest run src/features/ticket`.

    type: 'about:blank',

function respond(config: InternalAxiosRequestConfig, answer: Answer) {
  if (answer === 'pending') return new Promise<never>(() => undefined);

  const response = {
    data: answer.body,
    status: answer.status,
    statusText: String(answer.status),
    headers: new AxiosHeaders(),
    config,
  };

  if (answer.status < 300) return Promise.resolve(response);

  return Promise.reject(new AxiosError('failed', 'ERR_BAD_RESPONSE', config, null, response));
}

      );

    return (
      <SWRConfig value={{ provider: () => new Map(), shouldRetryOnError: false }}>

  id: string | null,
  item: RecordRead,
  seed: TicketStatusRow | undefined,

  return (
    id !== null &&
    item.data === undefined &&
    (seed === undefined || (item.error !== undefined && !item.error.retryable))

function breadcrumbLabel(
  id: string | null,
  record: TicketStatus | undefined,
  item: RecordRead,
): string | null | undefined {
  if (id === null) return undefined;
  const failureShown =
    item.data === undefined &&
    item.error !== undefined &&
    (record === undefined || !item.error.retryable);
  return failureShown ? null : record?.name;
}

function retryableFailure(result: ApiResult<TicketStatus> | undefined): SaveFailure | null {
  return result !== undefined && !result.ok && isRetryableCode(result.code) ? result : null;
}

  pending: TicketStatusFormValues | null,
  record: TicketStatus | undefined,
  label: string,
): readonly SummaryChange[] {

}

  const { create, update } = useSaveTicketStatuses(id);

  const guard = useUnsavedChanges(form.formState.isDirty && !mutation.isMutating);
  const lastSent = useRef<TicketStatusFormValues | null>(null);

    if (id !== null) await item.mutate(saved, { revalidate: false });

      const row: TicketStatusRow = { ...seed, ...saved };

        TICKETSTATUSES_PATH,
        row,

    router.push(readListReturn(LIST_BASE), { scroll: false });

    const outcome = await mutation.trigger(values);
    if (outcome.ok) {
      await afterSave(outcome.data);
      return { ok: true };

    if (outcome.code === VALIDATION_CODE) {

      flushSync(() => {

        for (const issue of issues.success ? issues.data : []) {
          const field = issue.path[0];

function isMessages(value: unknown): value is AbstractIntlMessages {
  return typeof value === 'object' && value !== null && !Array.isArray(value);
}

/** Deep-merges plain objects (message files hold no arrays); never mutates its inputs. */
function deepMerge(base: AbstractIntlMessages, over: AbstractIntlMessages): AbstractIntlMessages {
  const out: AbstractIntlMessages = { ...base };
  for (const [key, value] of Object.entries(over)) {
    const existing = out[key];
    out[key] = isMessages(existing) && isMessages(value) ? deepMerge(existing, value) : value;
  }
  return out;
}

/**

 * renders the English text rather than the key name (T-3-01).

export function messagesFor(locale: Locale): AbstractIntlMessages {
  const layers = locale === 'en' ? PACKS.en : [...PACKS.en, ...PACKS[locale]];
  return layers.reduce<AbstractIntlMessages>((acc, pack) => deepMerge(acc, pack), {});

/** Server render, browser parse, client hydration; returns the server HTML and React's recoverable errors. */
async function hydrate(tree: ReactElement): Promise<{ html: string; errors: unknown[] }> {
  const html = renderToString(tree);
  container = document.createElement('div');
  document.body.append(container);
  container.innerHTML = html;
  const errors: unknown[] = [];
  const target = container;
  await act(async () => {
    root = hydrateRoot(target, tree, {
      onRecoverableError: (error) => {
        errors.push(error);
      },
    });
    await Promise.resolve();
  });
  return { html, errors };
}
